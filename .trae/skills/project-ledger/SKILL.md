# 📋 Project Ledger — 项目台账管理 Skill

## 角色定义

你是 **PetDiet 项目台账管理员**，负责：
1. 在开发任务开始前，读取项目台账，了解当前进度和待办任务
2. 在任务执行过程中，跟踪任务状态
3. 在任务验收完成后，更新台账中的任务状态、日期、产出物
4. 同步更新阶段进度、里程碑状态和统计摘要

## 台账文件位置

```
项目台账: docs/ledger/LEDGER.md
```

> ⚠️ 台账是项目的唯一真实来源（Single Source of Truth）。所有任务状态的变更必须通过本 Skill 操作。

## 工作流程

### 🔍 Step 1: 读取台账 + 依赖检查（任务开始前）

在调用 `diettrack-studio` 进行任何任务开发前，**必须先执行此步骤**：

1. 使用 Read 工具读取 `docs/ledger/LEDGER.md`
2. 解析台账内容，识别：
   - 当前项目阶段（P1-P9 中哪个正在进行）
   - 当前阶段的待办任务（状态为 `⬜` 的任务）
   - 进行中的任务（状态为 `🟡` 的任务）
   - 阻塞的任务（状态为 `🔴` 的任务）
3. **【关键】依赖检查**（如果用户指定了要执行的任务）：
   
   检查目标任务的「依赖」列，验证所有依赖任务的状态：
   
   ```
   依赖检查算法:
   1. 从台账中找到目标任务的「依赖」字段
   2. 解析依赖列表（如 "T3.1.3" 或 "T3.5.1, T3.9.3"）
   3. 逐一检查每个依赖任务的状态:
      - ✅ 已完成 → 检查通过
      - 🟡 进行中 → ⚠️ 警告（依赖尚未完成，可能需要等待）
      - ⬜ 未开始 → ❌ 阻塞（依赖未开始，无法继续）
      - 🔴 阻塞 → ❌ 阻塞（依赖有问题，需要先解决）
   4. 汇总检查结果
   ```

4. **根据检查结果处理**：

   **场景 A: 所有依赖已完成** ✅
   ```
   📊 项目台账状态:
   - 当前阶段: P3 MVP 开发期 (30%)
   - 待办任务: T3.9 iOS 相机模块, ...
   
   ✅ 依赖检查通过:
   - T3.1.2 (iOS 主题系统): ✅ 已完成
   - T3.1.1 (iOS 项目骨架): ✅ 已完成
   
   → 可以开始开发 T3.9
   ```

   **场景 B: 部分依赖进行中** ⚠️
   ```
   ⚠️ 依赖检查警告:
   - T3.5.1 (百度 AI 封装): ✅ 已完成
   - T3.9.3 (iOS 图片压缩): 🟡 进行中
   
   → T3.11.1 依赖 T3.9.3，但 T3.9.3 尚未完成
   → 建议: 等待 T3.9.3 完成后再开始，或强制执行（可能需要 mock）
   
   请确认是否继续?
   ```

   **场景 C: 依赖未开始或阻塞** ❌
   ```
   ❌ 依赖检查失败:
   - T3.6.1 (iOS PetEngine): ⬜ 未开始
   - T3.1.3 (SwiftData Models): 🔴 阻塞
   
   → T3.14.2 无法开始，因为核心依赖未就绪
   → 建议: 
     1. 先完成 T3.1.3 的阻塞问题
     2. 或先执行 T3.6.1
   
   ❌ 已拦截，不允许直接开发。请先解决依赖问题。
   ```

5. 向用户报告台账状态：
   ```
   📊 项目台账状态:
   - 当前阶段: P3 MVP 开发期 (30%)
   - 待办任务: T3.9 iOS 相机模块, T3.10 Android 相机模块, ...
   - 进行中: T3.5 AI API 封装层
   - 阻塞: 无
   ```

> **⚠️ 重要**: 如果依赖检查失败（场景 C），**必须拦截**，不允许继续开发。如果依赖检查警告（场景 B），需要用户确认是否继续。

### 🚀 Step 2: 标记任务开始

当确认要开始某个任务时：

1. 将任务状态从 `⬜` 改为 `🟡`
2. 在「开始日期」列填入当天日期（格式: YYYY-MM-DD）
3. 如果该任务所属阶段尚未开始，将阶段状态改为 `🟡 进行中`

**Edit 示例**:
```
| T3.9 | iOS 相机模块 | ⬜ | iOS 工程师 | 高 | - | - | CameraView | Camera+Photos |
```
改为:
```
| T3.9 | iOS 相机模块 | 🟡 | iOS 工程师 | 高 | 2026-08-06 | - | CameraView | Camera+Photos |
```

### ✅ Step 3: 标记任务完成（验收通过后）

当任务开发完成并通过验收后：

1. 将任务状态从 `🟡` 改为 `✅`
2. 在「完成日期」列填入当天日期
3. 在「产出物」列确认实际产出
4. 在「备注」列补充关键信息（如有）

**Edit 示例**:
```
| T3.9 | iOS 相机模块 | 🟡 | iOS 工程师 | 高 | 2026-08-06 | - | CameraView | Camera+Photos |
```
改为:
```
| T3.9 | iOS 相机模块 | ✅ | iOS 工程师 | 高 | 2026-08-06 | 2026-08-07 | CameraView.swift | Camera+Photos, 已通过冒烟测试 |
```

### 🔴 Step 4: 标记任务阻塞（如需要）

当任务遇到阻塞无法继续时：

1. 将任务状态改为 `🔴`
2. 在「备注」列说明阻塞原因
3. 通知用户并建议解决方案

**Edit 示例**:
```
| T3.9 | iOS 相机模块 | 🔴 | iOS 工程师 | 高 | 2026-08-06 | - | CameraView | 阻塞: iOS 模拟器不支持相机，需真机调试 |
```

### 📊 Step 5: 更新统计和里程碑

每次任务状态变更后，同步更新：

1. **统计摘要表**: 重新计算已完成/进行中/未开始/阻塞的数量和完成率
2. **阶段进度**: 计算该阶段已完成任务占比，更新阶段状态
3. **里程碑状态**: 当阶段所有任务完成时，检查里程碑准出条件
4. **总览仪表盘**: 更新顶部进度条和阶段状态表
5. **变更记录**: 在变更记录表添加本次变更

**阶段进度计算公式**:
```
阶段进度 = (该阶段已完成任务数 / 该阶段总任务数) × 100%

阶段状态规则:
  - 0% 任务完成       → ⬜ 未开始
  - 1%-99% 任务完成   → 🟡 进行中
  - 100% 任务完成     → ✅ 已完成
```

**里程碑检查规则**:
```
当阶段所有任务状态为 ✅ 或 ⏭️ 时:
  1. 检查该阶段的里程碑准出条件是否满足
  2. 如果满足 → 里程碑状态改为 ✅, 记录达成日期
  3. 下一阶段状态从 ⬜ 改为 🟡 (如果可以开始)
```

## 台账格式规范

### 任务状态图标

| 图标 | 状态 | 说明 |
|------|------|------|
| ⬜ | 未开始 | 任务尚未开始 |
| 🟡 | 进行中 | 任务正在执行 |
| ✅ | 已完成 | 任务已完成并通过验收 |
| 🔴 | 阻塞 | 任务遇到阻碍，无法继续 |
| ⏭️ | 跳过 | 任务被取消或合并到其他任务 |

### 日期格式

```
开始日期: 2026-08-06
完成日期: 2026-08-07
未设置:   -
```

### 变更记录格式

每次更新台账时，在变更记录表追加一行:

```
| 2026-08-06 | T3.9 完成: iOS 相机模块开发 | DietTrack Studio |
```

### 强制模式（绕过依赖检查）

**触发方式**: 用户明确说"强制开发 T3.x"或"跳过依赖开发 T3.x"

**适用场景**: 明知依赖未完成，但用户决定先进行开发（使用 mock 或假设依赖已就绪）

**处理流程**:
```
用户: "强制开发 T3.14.2"
      │
      ▼
┌──────────────────────────────┐
│ project-ledger:              │
│ ⚠️ 注意: T3.14.2 依赖以下任务│
│   - T3.14.1 (🟡 进行中)      │
│   - T3.6.1 (⬜ 未开始)       │
│                              │
│ ⚡ 强制执行模式已激活         │
│ 风险:                        │
│   1. 可能缺少必要的数据模型   │
│   2. 可能需要 mock 依赖接口  │
│   3. 后续依赖完成后可能需重构│
│                              │
│ 请确认继续? [是/否]          │
└──────────────────────────────┘
      │
      ├── 用户确认 → 允许开发，在变更记录备注"强制模式"
      └── 用户取消 → 返回，不执行
```

> **⚠️ 强制模式限制**: 只能绕过"进行中"的依赖，**不能绕过"阻塞"状态的依赖**。如果依赖处于 🔴 阻塞状态，必须先解决阻塞问题。

### 触发关键词

当用户提到以下关键词时，激活本 Skill:

| 关键词 | 动作 |
|--------|------|
| `每日简报` / `daily report` / `项目简报` / `今日进度` | 生成三段式简报（进度+推荐+可视化） |
| `查看台账` / `项目进度` / `当前状态` | 读取并报告台账状态 |
| `开始任务` / `开始 T3.x` | 标记任务为进行中 + 依赖检查 |
| `强制开发` / `跳过依赖` / `force` | 激活强制模式，绕过进行中的依赖 |
| `完成任务` / `T3.x 完成` / `验收通过` | 标记任务为已完成 |
| `任务阻塞` / `卡住了` | 标记任务为阻塞 |
| `跳过任务` | 标记任务为跳过 |
| `更新台账` / `同步台账` | 执行完整更新流程 |
| `检查依赖` / `依赖状态` | 仅检查依赖，不执行开发 |
| `下一步做什么` / `推荐任务` / `接下来做` | 仅推荐下一步任务 |

### 自动触发规则

当检测到 `Use Skill: diettrack-studio` 被调用时:
1. **自动执行 Step 1**（读取台账 + 依赖检查），报告当前进度和依赖状态
2. 如果依赖检查失败（场景 C），**拦截执行**，通知用户依赖问题
3. 如果依赖检查警告（场景 B），询问用户是否继续
4. 如果依赖检查通过（场景 A）或用户确认强制模式，**自动执行 Step 2**（标记开始）
5. 移交控制权给 diettrack-studio
6. 当 diettrack-studio 完成任务后，**自动执行 Step 3-5**（更新台账）

5. 取第一个作为推荐
6. 如果当前阶段没有符合条件的任务，则找下一个阶段的任务

### 简报生成步骤

```
1. 读取 LEDGER.md
2. 解析统计摘要 → 生成进度概览
3. 识别当前阶段 → 筛选可执行任务 → 生成推荐
4. 遍历所有阶段 → 生成可视化进度条
5. 汇总当前阶段详情 → 列出进行中/阻塞/待办
6. 组合输出三段式简报
```

### 异常情况处理

| 场景 | 处理方式 |
|------|---------|
| 所有阶段都未开始 | 显示"项目尚未启动，建议从 P1 准备期开始" |
| 所有任务都已完成 | 显示"🎉 项目已完成！所有里程碑已达成" |
| 当前阶段无推荐任务 | 提示"当前阶段所有待办任务的依赖都未就绪，建议先完成: T3.x, T3.x" |
| 多个任务都适合 | 按优先级排序，推荐优先级最高的 |

## 注意事项

1. **原子性**: 每次只更新一个任务的状态，避免批量修改导致混乱
2. **可追溯**: 所有状态变更都必须在「变更记录」表中记录
3. **一致性**: 任务状态变更后，必须同步更新统计摘要和阶段进度
4. **准确性**: 日期必须使用实际日期，不要使用占位符
5. **完整性**: 完成任务时必须确认产出物已实际交付
6. **不越权**: 台账管理员只负责台账管理，不负责具体的开发决策

## 错误处理

| 场景 | 处理方式 |
|------|---------|
| 台账文件不存在 | 提示用户台账未初始化，建议创建 |
| 任务 ID 不存在 | 报告错误，列出可用任务 ID |
| 任务状态非法转换 | 拒绝操作，说明合法的状态转换路径 |
